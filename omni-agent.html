Omni-Agent

I. Tổng quan dự án

1. Tóm tắt dựa án (Executive Summary)

Omni-Agent là hệ thống event-driven hỗ trợ tìm kiếm kết hợp (RAG + Graph), quản lý/tạo test case và bug, tối ưu hóa truy xuất thông tin cho LLM.

2. Định nghĩa bài toán (Problem definition)

2.1. Test Cases Generation

Sau khi document (tài liệu yêu cầu, đặc tả, hướng dẫn...) đã được nhập vào hệ thống, thực hiện quy trình sau để tạo test case:

  1. Tiền xử lý document: Chuẩn hóa, phân đoạn, và phân loại các phần quan trọng (requirement, rule, scenario, v.v.).
  2. Sinh test case tự động: Sử dụng LLM hoặc module chuyên biệt để phân tích nội dung document, trích xuất các điều kiện kiểm thử, luồng chính/phụ, và sinh ra các test case sơ bộ.
  3. Kiểm tra & hiệu chỉnh: Người kiểm thử hoặc hệ thống kiểm tra lại test case, bổ sung hoặc chỉnh sửa cho phù hợp với thực tế nghiệp vụ.
  4. Liên kết với requirement: Gán các test case vừa tạo với các requirement, rule, hoặc scenario tương ứng trên đồ thị tri thức.
  5. Quản lý vòng đời: Đưa test case vào hệ thống quản lý (GNN-LM), phục vụ cho các hoạt động kiểm thử, phân tích ảnh hưởng, tối ưu hồi quy, v.v.

Lưu ý: Có thể tích hợp AI để tự động hóa bước sinh test case, hoặc thực hiện bán tự động tùy theo mức độ phức tạp của document và yêu cầu dự án.

2.2. Hybrid Search (RAG + Graph)

Xây dựng hệ thống kết hợp song song giữa RAG (Retrieval-Augmented Generation) và Graph Search nhằm tăng khả năng truy xuất thông tin và tư duy logic cho các LLM.

=> Knowledge Foundation (GNN-KF): mô-đun chịu trách nhiệm duy trì "chân lý" (ground truth) và ý đồ thiết kế của sản phẩm. Mô-đun này có thể được huấn luyện và tái sử dụng qua nhiều dự án cùng miền.

2.3. Test cases and bug management

Tối ưu hóa quản lý test case và bug (có thể tích hợp với công cụ như Jira).

Phân tích ảnh hưởng (Impact Analysis)

Ý tưởng: Khi một Requirement (ví dụ REQ-50) thay đổi, xác định node tương ứng trên đồ thị, lấy embedding (ví dụ từ GraphSAGE) và thực hiện tìm kiếm gần nhất trong không gian vector để tìm các TestCase có embedding giống.

Ưu điểm:

  • Không chỉ phát hiện TestCase có kết nối trực tiếp, mà còn tìm các TestCase tương đồng về ngữ nghĩa hoặc cấu trúc (ví dụ kiểm tra cùng DataEntity) — điều mà truy vấn đồ thị thuần túy có thể bỏ sót.
Tối ưu hóa hồi quy (Regression Test Optimization)

Quy trình:

  • Dùng GraphSAGE sinh embedding cho tất cả TestCase. Embedding phản ánh mối liên hệ ẩn như: feature hay thay đổi, module hay phát sinh bug...
  • Huấn luyện một mô hình đơn giản (ví dụ hồi quy tuyến tính) nhận embedding làm đầu vào để dự đoán "risk score" cho mỗi TestCase, dùng dữ liệu lịch sử (embedding, số lần phát hiện bug) làm nhãn.
  • Khi cần tối ưu hồi quy, tính embedding mới và chọn top-N TestCase có điểm rủi ro cao để ưu tiên chạy.
Phát hiện bug trùng lặp

Quy trình:

  • Khi có báo cáo bug mới (ví dụ Bug-123), tạo node và embedding ban đầu từ mô tả (SLM / PhoBERT...).
  • Chạy inference trên GraphSAGE để tổng hợp thông tin từ các hàng xóm và tạo embedding cuối cùng.
  • Tìm kiếm các bug có embedding gần nhất để đề xuất các ứng viên trùng lặp.
Gợi ý test case còn thiếu (Test Gap Analysis)

Ý tưởng: Bài toán link prediction. Huấn luyện GraphSAGE để học biểu diễn hợp lý; với một requirement (REQ-75) so sánh embedding của nó với embedding các TestCase khác để tính "compatibility score". Các TestCase có điểm cao nhưng chưa có liên kết là gợi ý kiểm thử bị bỏ sót.

Ví dụ thực tế (ngắn):

  • Impact Analysis: REQ-420 thay đổi → trả về 23 TC ưu tiên (12 liên kết trực tiếp, 8 tương đồng ngữ nghĩa, 3 module bị ảnh hưởng).
  • Regression Test Optimization: từ 5.000 TC chọn top‑100 (2%) có risk cao để chạy trước, phát hiện ~85% lỗi nghiêm trọng.
  • Duplicate Bug Detection: ticket “thanh toán thất bại” → tìm 2 bug gần giống (cosine 0.92, 0.87) → gợi ý duplicate.
  • Test Gap Analysis: REQ-75 → phát hiện 2 TC tương hợp >0.8 nhưng chưa cover → đề xuất tạo TC-addr-001.

=> Lifecycle Management (GNN-LM): mô-đun quản lý các sự kiện và hoạt động trong vòng đời phát triển và kiểm thử.

3. Mục tiêu & Mục đích (Goals & Objectives)

Mục tiêu tổng thể

  • Xây dựng hệ thống hỗ trợ tự động hóa kiểm thử phần mềm, tối ưu hóa quản lý test case và bug, nâng cao hiệu quả truy xuất thông tin cho LLM.
  • Tích hợp các công nghệ AI/ML (RAG, Graph, GNN) để tăng khả năng phân tích, đề xuất và kiểm thử thông minh.
  • Đảm bảo traceability giữa requirement, test case, bug và các thực thể nghiệp vụ, phục vụ phân tích ảnh hưởng và tối ưu hồi quy.
  • Tối ưu hóa quy trình kiểm thử, giảm chi phí và thời gian phát hiện lỗi nghiêm trọng.
  • Hỗ trợ mở rộng, tái sử dụng tri thức kiểm thử cho nhiều dự án cùng miền.

Mục đích cụ thể

  1. Tự động hóa sinh test case từ document, giảm phụ thuộc vào kiểm thử thủ công.
  2. Quản lý vòng đời test case và bug hiệu quả, tích hợp với các công cụ quản lý hiện có (Jira, CI/CD).
  3. Tăng khả năng phát hiện bug trùng lặp, test gap, và tối ưu hóa hồi quy dựa trên phân tích đồ thị và embedding.
  4. Hỗ trợ truy vấn thông minh, kết hợp RAG và Graph Search để trả lời các câu hỏi nghiệp vụ/phân tích.
  5. Đảm bảo hệ thống có khả năng mở rộng, bảo trì và tích hợp dễ dàng với các nền tảng khác.

3. Mô hình hóa dữ liệu (Data Modeling)

Mô tả cấu trúc node/edge cơ bản — phần này do LLM hỗ trợ tạo và kiểm soát (ví dụ: định dạng node type, edge type chuẩn hóa).

3.1. GNN-KF (Node / Edge cơ bản)

Node types (Ground truth / Product Intent)

Kết hợp các kĩ thuật:

Domain-Driven Design (DDD):

  • Node: Entity, ValueObject
  • Edge: HAS_ATTRIBUTE

Finite State Machine (FSM):

  • Node: State, Action,
  • Edge: CURRENT_STATE, ALLOWS_ACTIONS, TRANSITIONS_TO

Decision Logic

  • Node: Rule
  • Edge: REQUIRES_RULE, MEET_RULE

Định nghĩa Node Type

  1. Actor (Chủ thể): Trả lời câu hỏi "Ai đang thao tác?". Đây là những thực thể chủ động tác động vào hệ thống (Ví dụ: Người dùng (User), Quản trị viên (Admin), Hệ thống thanh toán bên thứ 3 (Momo)).
  2. Object (Đối tượng nghiệp vụ): Trả lời câu hỏi "Thao tác trên cái gì?". Đây là các thành phần hoặc cấu trúc dữ liệu chính chịu sự tác động, có định danh rõ ràng để phân biệt (Ví dụ: Đơn hàng (Order), Form đăng nhập, Hồ sơ người dùng).
  3. ValueObject (Dữ liệu chi tiết): Là các mẩu thông tin nhỏ lẻ cấu thành nên Actor hoặc Object. Chúng chỉ mang ý nghĩa chứa giá trị, không đứng độc lập (Ví dụ: Số điện thoại, Số tiền 100k, Chuỗi ký tự email).
  4. State (Trạng thái): Tình trạng hiện tại của Actor hoặc Object tại một mốc thời gian nhất định (Ví dụ: Đang chờ duyệt, Chưa đăng nhập, Đã khóa).
  5. Action (Hành động): Các thao tác làm thay đổi hệ thống hoặc kích hoạt luồng xử lý (Ví dụ: Bấm nút "Gửi", Gọi API tạo đơn hàng).
  6. Rule (Điều kiện/Quy tắc): Các chốt chặn logic (luật IF/ELSE) mà hệ thống bắt buộc phải kiểm tra để xem hành động có hợp lệ hay không (Ví dụ: Mật khẩu phải > 8 ký tự, Giỏ hàng phải có ít nhất 1 sản phẩm).
  7. Output (Kết quả trả về): Thứ hệ thống "nhả ra" sau khi hành động hoàn tất hoặc khi vi phạm Rule. Đây là căn cứ để xác nhận test case pass hay fail (Ví dụ: Mã HTTP 400 Bad Request, Dòng chữ báo lỗi màu đỏ trên màn hình, Json response).

Định nghĩa Edge Type

  1. PERFORMS (Actor -> Action): Chỉ định chủ thể thực hiện một hành động cụ thể (Ví dụ: User thực hiện Login). Thường dùng để xác định Role và kịch bản phân quyền (RBAC) trong test case.
  2. CAN_BE_IN (Actor hoặc Object -> State): Khai báo tập hợp các trạng thái hợp lệ mà một chủ thể hoặc đối tượng nghiệp vụ có thể tồn tại trong suốt vòng đời của nó (Ví dụ: Order có thể ở state Pending, Paid, hoặc Canceled).
  3. INTERACTS_WITH (Action -> Object): Xác định mục tiêu (target) mà hành động tác động trực tiếp lên. Trong UI test là các element (Button, Form); trong API test là các endpoint, URL, hoặc Controller.
  4. HAS_PROPERTY (Actor hoặc Object -> ValueObject): Mô tả các thuộc tính mang tính bản chất, định danh nghiệp vụ độc lập của một thực thể (Ví dụ: User có Email, PhoneNumber).
  5. CONTAINS (Object -> Object hoặc ValueObject): Mô tả quan hệ cha-con về mặt cấu trúc vật lý, dùng để build API Payload lồng nhau (Nested JSON) hoặc các thành phần Form UI phức tạp (Form chứa Input).
  6. ALLOWS_ACTION (State -> Action): Khai báo các hành động được phép thực thi khi đối tượng đang ở một trạng thái cụ thể. Dùng làm cơ sở để Agent duyệt đồ thị và sinh ra các kịch bản User Journey mạch lạc.
  7. TRANSITIONS_TO (Action -> State): Thể hiện sự thay đổi trạng thái của hệ thống hoặc đối tượng sau khi một hành động được thực hiện thành công (Happy Path).
  8. REQUIRES_RULE (Action -> Rule): Khai báo các điều kiện ràng buộc, kiểm tra hợp lệ (validation/business logic) mà hệ thống bắt buộc phải đánh giá khi hành động được kích hoạt.
  9. MEET_RULE (Rule -> State): Xác định trạng thái mới của đối tượng/hệ thống nếu hành động vượt qua (pass) thành công các điều kiện ràng buộc của Rule.
  10. PRODUCES (Action -> Output): Định nghĩa kết quả trực tiếp trả về từ hệ thống sau một hành động thành công. Dùng làm Expected Result (Assertion) cho Happy Path (Ví dụ: HTTP 200 OK, Load trang Dashboard).
  11. FAILS_WITH (Rule -> Output): Định nghĩa hệ quả hoặc phản hồi báo lỗi của hệ thống khi điều kiện ràng buộc bị vi phạm. Dùng làm Expected Result (Assertion) cho Negative/Unhappy Path (Ví dụ: HTTP 400 Bad Request, hiển thị text lỗi đỏ trên UI).

Có thể sinh test cases theo quy tắc Model-Based Testing (MBT):

Action + Rule
    → 1 Positive Test
    → N Negative Tests

actor 
  → PERFORMS → action 
      → REQUIRES_RULE → rule 
              → MEET_RULE → state 
                    → ALLOWS_ACTION → next action   ← KEY CONNECTOR
              → FAILS_WITH → output (negative path)
      → TRANSITIONS_TO → state
              → ALLOWS_ACTION → next action          ← KEY CONNECTOR
Example System Prompt 
# Role and Intent
- **Role:** You are a leading expert in the field of `Business Analysis`.
- **Task Background:** You are receiving a request to extract nodes, edges, and relationships from a text chunk for the purpose of `building a graph`.
- **Core Goal:** Perform the task below with in-depth thinking, rigorous logic, and a multi-faceted perspective.

# INPUT SCHEMA
The user's input data is organized within the following XML tags:
- `<toc>`: This section contains the Table of Contents of the document, which provides an overview of the document's structure and main topics.
- `<chunk>`: This is a chunk from the document.

# DELIVERABLES
- **Format:** TOON (Token-Oriented Object Notation)
- **Tone & Style:** Concise, problem-focused
- **Output Structure:**
```toon
nodes(id, name, type):
n1, "entity name", "node type"
n2, "entity name", "node type"
edges(id, name):
e1, "edge name"
e2, "edge name"
relationships(id, src_node_id, edge_id, des_node_id):
r1, n1, e1, n2
r2, n2, e2, n1
...
```
# GRAPH DEFINITION
## Definition of Node Type
**Actor**: Answers the question "Who is performing the action?". These are the active entities that interact with the system (e.g., User, Admin, Third-party payment system such as Momo).
**Object (Business Object)**: Answers the question "Operating on what?". These are the main components or data structures being affected, clearly identifiable to distinguish between them (e.g., Order, Login Form, User Profile).
**ValueObject (Detailed Data)**: Small pieces of information that make up Actor or Object. They only hold values and cannot stand alone (e.g., Phone number, Amount 100k, Email string).
**State**: The current condition of an Actor or Object at a specific point in time (e.g., Pending approval, Not logged in, Locked).
**Action**: Operations that change the system or trigger process flows (e.g., Click "Submit" button, Call API to create order).
**Rule (Condition/Rule)**: Logical checkpoints (IF/ELSE statements) that the system must verify to determine if an action is valid (e.g., Password must be > 8 characters, Cart must have at least 1 item).
**Output (Return Result)**: What the system "returns" after an action is completed or when a Rule is violated. These are used to verify whether a test case passes or fails (e.g., HTTP 400 Bad Request, Red error message on the screen, JSON response).
## Definition of Edge Type
**PERFORMS (Actor -> Action)**: Specifies the subject performing a particular action (e.g., User performs Login). Commonly used to define Role and authorization scenarios (RBAC) in test cases.
**CAN_BE_IN (Actor or Object -> State)**: Declares the set of valid states that an Actor or Business Object can exist in throughout its lifecycle (e.g., Order can be in states Pending, Paid, or Canceled).
**INTERACTS_WITH (Action -> Object)**: Identifies the target that the action directly affects. In UI tests, these are elements (Button, Form); in API tests, endpoints, URLs, or Controllers.
**HAS_PROPERTY (Actor or Object -> ValueObject)**: Describes inherent properties, the business-identifying attributes of an entity (e.g., User has Email, PhoneNumber).
**CONTAINS (Object -> Object or ValueObject)**: Describes parent-child structural relationships, used for building nested API payloads (Nested JSON) or complex Form UI components (Form containing Input).
**ALLOWS_ACTION (State -> Action)**: Declares the actions that are permissible when the object is in a specific state. Used as a basis for Agents to traverse the graph and generate coherent User Journey scenarios.
**TRANSITIONS_TO (Action -> State)**: Represents the change of state of the system or object after an action is successfully performed (Happy Path).
**REQUIRES_RULE (Action -> Rule)**: Declares the constraints and validation/business logic that the system must evaluate when the action is triggered.
**MEET_RULE (Rule -> State)**: Determines the new state of the object/system if the action successfully passes all Rule constraints.
**PRODUCES (Action -> Output)**: Defines the direct output returned by the system after a successful action. Used as the Expected Result (Assertion) for the Happy Path (e.g., HTTP 200 OK, Load Dashboard page).
**FAILS_WITH (Rule -> Output)**: Defines the consequence or error response from the system when a rule constraint is violated. Used as the Expected Result (Assertion) for Negative/Unhappy Path (e.g., HTTP 400 Bad Request, displaying red error text on UI).
